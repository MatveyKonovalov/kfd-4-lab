## 3. Реализация приложения

Разработан анализатор репозитория, который позволяет:

- обходить файловую структуру указанного каталога;
- подсчитывать количество файлов и строк по расширениям;
- определять три наиболее длинных файла;
- обрабатывать пустые файлы;
- корректно реагировать на некорректный путь к каталогу.

Реализация выполнена на Kotlin.

---
## 4. Модульная архитектура

После реализации монолитной версии приложение было разделено на два модуля.

**Модуль `core`:**
- обход файловой системы;
- сбор информации о файлах;
- подсчёт статистики;
- сортировка результатов;
- основная логика анализа.

**Модуль `cli`:**
- обработка аргументов командной строки;
- вызов функций анализатора;
- форматирование и вывод результатов;
- обработка пользовательского ввода.

Модуль `cli` использует функциональность `core`. При этом основная логика анализа не зависит от интерфейса командной строки.

---
## 5. Тестирование

Для проверки корректности работы реализованы автоматические тесты.

Проверены следующие сценарии:

1. Успешный анализ каталога с файлами.
2. Анализ пустого каталога.
3. Обработка некорректного пути к каталогу.

По результатам последнего запуска все три теста завершились успешно:

- `test empty directory 2 expect empty reports()` — PASSED;
- `test incorrect directory path expect exception()` — PASSED;
- `test directory 1 expect success()` — PASSED.

## 6. Сборка и запуск

Для сборки проекта используется Gradle Wrapper:

```bash
./gradlew build
```

Для запуска приложения с указанием каталога:

```bash
./gradlew run --args="core/src/test/kotlin/testdirectories/test1"
```

В качестве аргумента передаётся путь к анализируемому каталогу.

## 8. Эксперимент с инкрементальной сборкой Gradle

Для проверки инкрементальной сборки были выполнены два запуска Gradle.

Первый запуск:

```bash
./gradlew build --no-configuration-cache --no-build-cache --console=plain
```

Результат:

```text
BUILD SUCCESSFUL in 1s
10 actionable tasks: 10 up-to-date
```

Все задачи имели статус `UP-TO-DATE`, поскольку исходные файлы не изменялись.

После изменения исходного кода был выполнен повторный запуск той же команды.

Результат:

```text
BUILD SUCCESSFUL in 13s
10 actionable tasks: 6 executed, 4 up-to-date
```

Gradle обнаружил изменения и повторно выполнил необходимые задачи, включая:

- `:core:compileKotlin`;
- `:core:jar`;
- `:core:test`.

При этом задачи, не затронутые изменениями, остались актуальными.

Все три автоматических теста завершились успешно.

Таким образом, эксперимент подтвердил работу инкрементальной сборки Gradle: система повторно выполняет только те задачи, результаты которых необходимо обновить после изменения исходного кода.

Были реализованы автоматические тесты, проверяющие основные сценарии работы приложения. Все три теста успешно пройдены.

Также был проведён эксперимент с инкрементальной сборкой Gradle. Полученные результаты показали, что после изменения исходного кода повторно выполняются только необходимые задачи, а остальные используют актуальные результаты предыдущей сборки.

Поставленные задачи по реализации приложения, модульному разделению, тестированию и изучению инкрементальной сборки выполнены.
